You are acting as a senior full-stack software engineer, solution architect, AI engineer, product designer, and technical lead. Build a functional hackathon MVP called “The City Around You”.

The goal is to create an AI-powered civic intelligence and complaint management platform for Karachi. The platform allows citizens to report civic problems using text, voice, photographs, or video. AI understands the report, classifies the issue, determines the responsible authority, evaluates urgency, checks whether the reported location is near a sensitive location, evaluates report authenticity, generates a properly formatted complaint, and routes it to the appropriate authority. Authorities can manage, prioritize, assign, investigate, update, and resolve cases. Administrators can manage citizens, authorities, system configuration, routing rules, sensitive locations, and suspicious reports.

This is a hackathon prototype, so prioritize a polished, convincing, fully working end-to-end experience over production-level complexity. Build the core flows completely and use realistic mocked integrations where actual government APIs or external systems are unavailable. Do not create fake functionality that appears to work but has no underlying implementation. Clearly separate mocked integrations from real functionality.

Before making any destructive change, deleting existing functionality, changing project architecture, installing major dependencies, changing environment configuration, modifying authentication, changing database structure, or overwriting existing code, first explain what you intend to change and ask for permission. Do not make assumptions about existing project conventions. Inspect the existing project before making architectural decisions. Preserve useful existing code and follow the project's established patterns when appropriate.

The primary product statement is:

“Describe what is wrong. AI understands it, determines who should handle it, decides how urgent it is, checks its authenticity, and helps make sure it actually gets resolved.”

The product should have three primary roles.

1. Citizen / Reporter

A citizen can register and log in using identity information including CNIC, phone number, and email. Treat the CNIC as sensitive information. Do not display it unnecessarily throughout the application. Internally associate the citizen with a unique citizen ID and use that ID throughout normal application workflows.

The citizen dashboard should allow the user to:

* Create a civic report.
* Upload a photograph.
* Upload a video where supported.
* Record or upload a voice report where supported.
* Enter a typed description.
* Submit the report in English, Urdu, or Roman Urdu.
* Select or confirm the issue location.
* Review the AI interpretation before final submission.
* See the detected issue category.
* See the recommended authority.
* See the priority level.
* See whether a sensitive location is nearby.
* See report verification status.
* Submit the complaint.
* Track complaint progress.
* Receive updates.
* Respond to verification requests.
* Confirm whether an issue has actually been resolved.
* Reject a resolution if the issue remains.
* View their previous reports.
* View relevant nearby civic incidents where appropriate.

The citizen reporting experience should be extremely simple. Do not force the user to complete a long government-style form. Let AI extract as much information as possible from the citizen’s natural input and only ask additional questions when the missing information would materially affect routing, priority, verification, or resolution.

The system must support natural language such as:

“Yahan do din se gutter ka pani road par khara hai aur school ke bachay isi raste se guzarte hain.”

The system should be capable of converting this into structured information such as:

Issue: Sewage overflow

Duration: Approximately two days
Nearby sensitive location: School
Potential impact: Pedestrian and public-health risk
Recommended authority: Appropriate water/sewerage authority
Priority: High or Critical depending on the rules
Language: Urdu/Roman Urdu
Complaint summary: Generated automatically

The AI system must perform the following major functions.

1. Report understanding and classification

Analyze text, voice transcripts, photographs, and video descriptions or extracted visual information where supported.

Classify the report into configurable civic issue categories. The initial categories should include:

* Water leakage
* Burst water line
* Water outage
* Low water pressure
* Sewage overflow
* Blocked drain
* Open manhole
* Garbage accumulation
* Uncollected waste
* Illegal dumping
* Construction waste
* Road damage
* Pothole
* Road flooding
* Footpath damage
* Footpath encroachment
* Streetlight failure
* Traffic sign damage
* Public infrastructure damage
* Environmental pollution
* Burning waste
* Other

Do not assume the category list is permanent. Store issue categories as configurable data.

The AI should produce structured output rather than only natural-language text. At minimum, the internal AI result should contain:

Use strong schema validation for AI responses. Never trust free-form AI output directly in business logic.

2. Authority routing

The system must determine which authority is responsible for the reported issue.

Do not rely exclusively on an LLM to decide this.

Create a configurable routing layer that combines:

* Issue category
* Geographic service area
* Authority responsibility
* Location
* Existing routing rules
* AI classification
* Administrative overrides

The AI should interpret the messy citizen input. The routing engine should apply deterministic rules and configured authority ownership.

The system should be able to explain why an authority was selected.

For example:

“Recommended authority: KW&SC. Reason: the report indicates sewage overflow and drainage-related infrastructure.”

Display an authority confidence score, but do not present confidence as mathematical certainty.

3. AI priority and severity engine

Every report must receive a priority classification:

Low
Medium
High
Critical

The priority must not be based solely on the LLM’s opinion.

Use a combined decision model that considers:

* Type of issue
* Severity
* Potential danger
* Public health risk
* Duration
* Estimated affected population
* Road or infrastructure importance
* Proximity to sensitive locations
* Number of related citizen reports
* Evidence quality
* Potential escalation risk

Use a deterministic rules layer to adjust AI recommendations.

For example:

Base severity: High
Nearby hospital: Priority increase
Major road affected: Priority increase
Many citizens affected: Priority increase
Long duration: Priority increase

Final result: Critical

The system must show the primary factors that influenced the priority decision.

4. Sensitive location detection

Create a dedicated sensitive-location system.

Sensitive locations should include configurable categories such as:

* Hospitals
* Clinics
* Emergency facilities
* Schools
* Universities
* Day-care facilities
* Old-age homes
* Orphanages
* Special-needs facilities
* Public transport hubs
* Major markets
* Major public gathering locations
* Other locations defined by administrators

For every civic report, evaluate whether the reported issue is near a sensitive location.

Use actual geographic distance where reliable coordinates are available.

Do not rely only on distance.

The relevance of the sensitive location should consider:

* Distance
* Issue type
* Potential spread or impact
* Direction of the problem where available
* Facility type
* Expected number of affected people

For example, a sewer overflow 200 metres from a hospital may be more significant than a minor pavement defect 50 metres away.

The result should include:

sensitiveLocationDetected
sensitiveLocationType
sensitiveLocationName
distance
relevance
impactAssessment
priorityAdjustment

If no sensitive location exists, explicitly return that none was detected.

5. Authenticity and false-report detection

Create an AI-assisted report authenticity system.

Do not allow the AI to make a final accusation that a citizen has submitted a fake report.

Possible states should include:

Unverified
Likely Genuine
Needs Verification
Suspicious
Confirmed False

Evaluate signals such as:

* Image/report mismatch
* Duplicate image
* Reused evidence
* Location mismatch
* Description/location inconsistency
* Repeated suspicious behavior
* Contradictory evidence
* Repeated confirmed false reports
* Evidence that the image or video may not correspond to the current incident

Use an authenticity risk score to identify cases requiring manual verification.

Example:

Authenticity Risk: 81/100
Reason: Evidence appears inconsistent with the reported location.

Do not automatically penalize the citizen solely because the AI produces a high risk score.

6. Human verification workflow

7. False-report penalty workflow

The product should support a future penalty/challan mechanism, but it must be designed with due process.

Never automatically issue a penalty solely because an AI model classified something as false.

The workflow should be:

Suspicious report

→ Citizen clarification
→ Admin review where appropriate
→ Confirmed false or malicious
